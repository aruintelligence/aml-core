# ĀML™ — 90-Day Mainstream Adoption Plan

Goal: move ĀML from a strong reference implementation into a technology that independent developers, AI teams, enterprises, researchers, and standards participants can encounter, test, integrate, and challenge within months.

This plan prioritizes **distribution, interoperability, credibility, and adoption** over feature accumulation.

## North-star positioning

> **ĀML™ is the accountability layer between AI intent and the human interface.**

AI proposes. ĀML evaluates. Existing UI renders. The receipt explains.

## Days 0–30 — Distribution

### Public package distribution

- publish a stable JavaScript package through a mainstream registry;
- reserve and document canonical package names before promoting them;
- verify provenance and release integrity;
- provide copy-paste browser, Node, React, and Next.js quickstarts;
- publish signed release artifacts where practical.

### Framework adoption

Ship maintained examples or adapters for:

- React;
- Next.js;
- Vite/plain browser JavaScript;
- Web Components;
- AI-generated UI pipelines.

### GitHub-native adoption

- Meaning Gate™ reusable GitHub Action;
- semantic/policy diff PR reporting;
- one-click starter workflows;
- AML conformance workflow;
- issue templates for integrations, adversarial testing, accessibility, and commercial relationships.

### Public demo

Maintain one flagship demonstration that shows:

1. an AI-generated interface proposal;
2. declared meaning;
3. policy/accessibility/privacy/consent evaluation;
4. allow/suppress/transformation outcome;
5. execution receipt;
6. View Meaning™;
7. semantic/policy diff;
8. proof-carrying interface.

A stranger should understand the project in under 60 seconds.

## Days 31–60 — Independent credibility

### Second implementation

A second runtime must implement the published protocol contracts **without importing the reference implementation**.

Target:

- wire negotiation;
- canonical serialization;
- policy passport verification;
- execution receipt verification;
- content-addressed bundles;
- conformance claims;
- causal graphs;
- brand-authorization verification where implemented.

Any ambiguity discovered should become an RFC issue.

### Security review

Invite independent attacks against:

- receipt integrity;
- signature handling;
- replay resistance;
- policy packs;
- capability tokens;
- delegated trust;
- revocation;
- transparency logs;
- proof-carrying interface binding.

Publish failures and fixes.

### Accessibility scrutiny

Invite accessibility practitioners to test:

- reduced-motion behavior;
- keyboard declarations;
- text alternatives;
- contrast policies;
- cognitive-load declarations;
- the limits of the current model.

Do not market AML as WCAG replacement.

### Research reproducibility

- stable benchmark fixtures;
- immutable test vectors;
- citation metadata;
- explicit evidence boundaries;
- reproducible protocol tests.

## Days 61–90 — Ecosystem and enterprise

### Enterprise pilot kit

Create a minimal pilot path for an existing AI product:

- wrap one component or generated interface;
- declare intent/meaning;
- select a policy profile;
- produce signed receipts;
- enable View Meaning;
- add Meaning Gate to CI;
- generate a pilot report.

The pilot should not require rewriting the application.

### Official commercial layer

Keep separate:

- MIT software rights;
- technical conformance;
- official ĀML / ĀRU brand authorization;
- enterprise/OEM services;
- managed infrastructure;
- strategic partnerships.

Official brand rights may be represented by signed `aml-brand-authorization/1` credentials after an appropriate written agreement.

### Standards outreach

Prepare the project for informed discussion with:

- browser/runtime communities;
- AI framework maintainers;
- accessibility communities;
- security/identity engineers;
- academic HCI / accountable-AI researchers;
- standards practitioners.

Do not claim standards-body adoption before it occurs.

### Public launch surfaces

Prepare concise, evidence-bound material for:

- developer communities;
- technical forums;
- open-source communities;
- AI engineering communities;
- academic/research audiences;
- enterprise AI teams.

Lead with working code and reproducibility, not grandiose claims.

## Adoption metrics worth tracking

Track metrics that reflect real use:

- independent clones/forks/contributors;
- successful conformance runs outside the reference repo;
- package downloads after a verified registry release;
- starter-kit usage;
- external integrations;
- independent bug/security reports;
- second-runtime interoperability passes;
- enterprise pilot conversations;
- official authorization/licensing inquiries;
- citations/research references.

Do not manufacture stars, testimonials, users, partnerships, citations, or compatibility claims.

## What success looks like after 90 days

ĀML should no longer depend on one explanation or one repository. A serious evaluator should be able to:

1. discover it through search, GitHub, AI tooling, or a framework example;
2. understand the core value in one minute;
3. try it without installing anything;
4. integrate it into an existing application;
5. verify its protocol behavior independently;
6. challenge its security and assumptions;
7. distinguish open software from official AML branding;
8. contact ĀRU immediately when an official commercial relationship is desired.
