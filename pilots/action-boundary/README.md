# Proposed action boundary — a small ĀML pilot

Agents can propose a tool call; the host must decide whether to dispatch it. This reference pilot freezes a proposed action as canonical JSON, hashes its exact semantics, checks an exact-match host policy, and binds a host approval to that proposal digest before dispatch. The execution callback receives the frozen proposal, even if the original object changes while approval is pending.

**Revoke before local handoff:** `createLocalRevocationHandoff()` in [`local-revocation-handoff.mjs`](local-revocation-handoff.mjs) is a separate, process-local reference for the [authority race proposal](https://github.com/aruintelligence/aml-core/pull/422). After the trusted host authenticates an approval, it calls `issue({ tenant, issuer, actor, audience, tool, policy, preparedRequest })`. The resulting grant binds canonical hashes of the complete prepared request and policy plus all five identity fields. A `revokeIssuer({ tenant, issuer })` increments that tenant's issuer epoch. `dispatch({ grant_id, ...sameHostInputs, execute })` checks the live epoch and host clock, spends one grant, and **invokes** the callback synchronously with the frozen request before its first await. Changed BCC, policy, audience, tenant, or tool blocks before the callback. An uncertain callback outcome remains spent. Run `node --test test/action-boundary-local-revocation-handoff.test.js` for the adversarial cases.

The local guarantee ends at callback invocation. An asynchronous callback can wait before contacting its provider; revocation in that interval cannot be ruled out by this module. Only code inside one Node process shares this epoch and grant state. It is not a durable or cross-worker authority store, does not authenticate the approver, evaluate the policy, prove provider acceptance, or prevent calls that bypass it. The host must own every input and perform its actual policy and identity checks before issuing the grant. A deployment needs a shared transactional authority boundary at the provider handoff, stable idempotency and reconciliation, and independent integration evidence before claiming live revocation protection. The design proposal's broader acceptance gates remain open.

**Serialize multiple local workers:** [`createFileRevocationHandoff`](file-revocation-handoff.mjs) extends the same canonical binding to separate Node processes on **one trusted local filesystem**. It stores short-lived grants, tenant-scoped issuer epochs, and a monotonic observed host clock in a private directory. It rejects a symlink anywhere in the directory ancestry, a group/world-writable parent without the sticky bit, and a changed directory identity within one authority instance. A private exclusive directory lock orders grant issuance, revocation, one-use claim, and synchronous callback invocation. `revokeIssuer()` invalidates grants issued at an earlier epoch; it does not permanently suspend the issuer or prevent the trusted host from issuing a new grant. The claim is synced before the callback. A crash after the claim leaves the grant spent; a crash while holding the lock strands it and all later operations fail closed until an operator investigates. Run `node --test test/action-boundary-file-revocation-handoff.test.js` to exercise two child processes racing one grant, a second process revoking it, path replacement, a crash, BCC/policy/tenant changes, clock rollback, and uncertain provider results. Every callback in these tests is simulated.

The host must authenticate the approving human or service and check its real policy **before** calling `issue()`. It must build the exact provider request before approval, then pass the same trusted context and prepared request to `dispatch()`. Tenant, issuer, actor, audience, and tool must be stable canonical IDs; leading/trailing whitespace, control characters, and non-NFC forms are rejected, but the host still owns identity normalization and authentication. A caller-supplied `now` is ignored. The callback receives a frozen copy of that request and a stable idempotency key, but the host must use its provider's idempotency contract and verify that the callback starts the actual handoff before yielding. A successful `returned` result means only that the callback returned. A thrown or rejected callback is `outcome_unknown`; no automatic retry is permitted.

**Anchor a one-use claim outside the local authority store:** An optional host-owned `claimOnce` hook can preserve a spent grant across an older copy of the authority directory and a process restart. Pass it to `createFileRevocationHandoff({ directory, claimOnce })`. It receives a frozen `{ protocol: "aml-file-authority-external-claim/1", claim_key_sha256, binding_sha256 }` record. When a grant has a host `operationId`, the claim key is the stable SHA-256 operation hash for tenant, issuer, and that ID, so an older local snapshot cannot send the same host intent with a newly minted grant. For a direct grant without an operation ID, the key is the SHA-256 idempotency key for tenant and grant ID. The binding digest identifies the exact prepared request and host context. The host must implement an atomic, durable, linearizable insert-if-absent keyed by `claim_key_sha256`, retain it independently of authority-directory rollback, and return **exactly `true` only after a new claim is committed**, `false` when the key already exists, or throw on uncertainty. A repeated key with a different binding must never return `true`. For example, a host may adapt a trusted transactional store:

```js
const authority = createFileRevocationHandoff({
  directory: privateLocalDirectory,
  claimOnce: ({ claim_key_sha256, binding_sha256 }) =>
    trustedStore.insertIfAbsent(claim_key_sha256, binding_sha256)
});
```

The local spent marker is synced **before** `claimOnce` runs. The local authority lock remains held while an asynchronous claim is pending, and the operation marker, host clock, grant expiry, and directory identity are checked again before the callback. A `false` result blocks with `external_claim_spent`; a throw, rejection, or nonboolean result is `external_claim_unavailable` and indeterminate. Neither case invokes the callback; both leave the local grant spent. A busy revocation must be retained and retried. A claim that hangs leaves the lock busy; after a crash, reconcile it against the external store and provider before recovery. [`testing-claim-anchor.mjs`](testing-claim-anchor.mjs) uses a separate local file directory only to reproduce a rollback across processes in tests; it is not a production anchor or protection against same-user tampering.

**Preserve issuer revocation across local rollback:** For deployments that need to reject *unspent* grants from an older authority snapshot, pass an `epochAnchor` with `claimOnce` and `advanceEpoch` backed by the **same independently held, durable, linearizable host store**. This option is separate from the spent-only `claimOnce` option. Call `await authority.revokeIssuerAnchored({ tenant, issuer })` for every revocation; `revokeIssuer()` refuses to run when an epoch anchor is configured. The anchor's `advanceEpoch` receives frozen `{ protocol: "aml-file-authority-external-epoch/1", issuer_sha256, expected_epoch, next_epoch }` and must atomically compare the held epoch (initially zero) with `expected_epoch`, durably set `next_epoch`, then return exactly `true`. It returns `false` on a mismatch and throws on uncertainty. Its `claimOnce` receives frozen `{ protocol: "aml-file-authority-external-claim/2", claim_key_sha256, binding_sha256, issuer_sha256, epoch }` and must **in one atomic transaction** verify the held issuer epoch equals `epoch` and insert the unused claim key, returning exactly `true` only after both checks commit. A duplicate claim or epoch mismatch returns `false`; an uncertain result throws. For example, the host can adapt a transactional service:

```js
const authority = createFileRevocationHandoff({
  directory: privateLocalDirectory,
  epochAnchor: {
    advanceEpoch: record => trustedStore.compareAndAdvanceIssuer(record),
    claimOnce: record => trustedStore.claimIfIssuerEpochMatches(record)
  }
});
const revoked = await authority.revokeIssuerAnchored({ tenant, issuer });
```

The host must keep that store independent of the local authority directory and retain both its epochs and claims through local rollback. The local lock spans the external epoch update and local epoch write; a rejected or uncertain advance leaves the lock stranded for operator reconciliation. A restored old directory can still issue a stale grant, but the epoch-aware external claim rejects it before the callback. [`testing-epoch-anchor.mjs`](testing-epoch-anchor.mjs) demonstrates the protocol with separate local files and a cross-process rollback test; it is not a production database, multi-machine authority, or tamper-resistant store. All participating local workers and revocation routes must use the **same** local authority lock; independent local stores can race an external advance after a claim and before provider handoff. An anchor outage blocks callbacks, and a returned callback remains no proof of provider acceptance.

**Bind approval to a pre-revocation epoch:** [`createRevocablePreparedMailToolExecute`](REVOCABLE_PREPARED_MAIL.md) is an opt-in host adapter for a prepared mail request and this file store. `observeIssuer()` reads the tenant/issuer epoch under the authority lock before the host awaits authenticated approval. After exact digest approval and an unchanged policy check, `issue(..., { expectedEpoch })` conditionally creates the grant under that same lock; a revocation during approval blocks issuance without storing an unapproved grant. Revocation between issuance and callback invocation is checked again by `dispatch()`. The integration tests include cross-process revocation during both windows and an in-memory sender; no live mail provider is involved.

**Bind one host intent across retries:** The adapter now requires `operationIdFor(context)` to return a stable host-generated ID. `issue(..., { operationId })` writes a durable operation marker under the same authority lock **before** the grant, scoped to tenant and issuer. Another worker cannot issue a second grant for that operation, even when a fresh approval returns the same digest. Reusing the ID with a different request or policy blocks as a mismatch; a new intended send must use a new ID and approval. The optional `operationId` on the lower-level `issue()` preserves its older direct-call behavior when omitted. These markers need deliberate retention and operator reconciliation after uncertain or lost sends. The local operation marker alone assumes the store is preserved; a fresh instance needs an independently retained external claim or checkpoint to withstand an older restored directory.

**Detect a restored local snapshot:** [The opt-in checkpoint](AUTHORITY_CHECKPOINT.md) records issue, revoke, and claim transitions in a separate host-controlled anchor before their local records become usable. New protocol-2 stores also bind their grant, epoch, operation, and spent-claim files to that anchor. A child process with an older restored authority directory or selectively missing epoch or spent marker blocks before its simulated provider callback. Existing protocol-1 stores retain only whole-directory rollback detection. The bundled `createFileAuthorityAnchor` is a separate local file example, not an independently operated service; restoring both directories together still defeats this check. Anchored and unanchored workers cannot safely share one authority.

The checkpoint and `epochAnchor` are alternative revocation protections and cannot be configured together. Protocol 2 detects selective changes to committed local decision files before issue or dispatch if its separately retained state stays current. The epoch-aware claim checks the independently held issuer epoch at dispatch. The checkpoint can be combined with spent-only `claimOnce`.

This reference is deliberately unavailable after a crashed lock. **Do not automatically remove the lock, replace the authority directory, or issue a replacement grant**: first reconcile the claimed operation against provider records, any external state, and the persisted outcome, then follow an operator-controlled recovery procedure appropriate to the host. The pinned directory identity detects replacement only during the lifetime of that instance. The spent-only `claimOnce` hook protects a spent grant or host operation while its independently held claims remain durable and the host retains its operation ID. The epoch-aware claim additionally rejects an old unspent grant after local epoch rollback; the checkpoint detects a restored older authority directory while its external state stays current. No option protects a replaced or rolled-back external store or makes the local store tamper resistant. The module does not supply a production external store, an operator recovery procedure, authenticated approvals, policy evaluation, distributed consensus, network filesystem locking, store tamper resistance against another process with the same OS identity, or protection for tools that bypass the gate. If revocation attempts find the lock busy, the host must retain the pending revocation and retry it; a busy response does not mean revocation took effect. Provider-side revocation-at-handoff and a production multi-machine claim remain unproven.

The published [`vectors.json`](vectors.json) contains six exact proposal digests and decisions, including reordered keys, a changed destination, a changed body, and an undeclared effect. The executable Python action boundary adds dispatch behavior for the same restricted wire subset: JSON integers within JavaScript's safe range, BMP-only object keys, and Unicode-scalar string values. Unsupported floats, non-BMP keys, and lone-surrogate values are rejected as `unsupported_json_subset` rather than silently producing a different digest. Numeric array-index object keys follow JavaScript's actual wire order: canonical decimal `0` through `4294967294` first in ascending numeric order; all remaining BMP keys in lexical order. This restriction is narrower than the JavaScript reference implementation; agreement is claimed only for the stated domain and checked cases, not every possible JSON input.

## Contract

```json
{
  "protocol": "aml-proposed-action/1",
  "tool": "send_message",
  "effect": "send",
  "resource": "team@example.test",
  "purpose": "Send a status update",
  "arguments": { "subject": "Update", "body": "The build passed." }
}
```

The separate policy has protocol `aml-action-policy/1` and exact rules with `tool`, `effect`, `resource`, and `requires_approval`. Unknown, malformed, and ambiguous policies deny. No wildcards or URL-prefix rules are supported. Supported effect labels are `read`, `write`, `send`, `pay`, and `delete`; they are declarations, not automatic classifications. The host must map the real tool and resource correctly. The host approval callback must return `{ approved: true, proposal_sha256 }` for the frozen proposal; an untrusted string with that shape is not proof of a person's consent.

The dispatch receipt records `blocked`, `dispatched`, or `unknown`. `dispatched` means the host callback returned; it does not prove delivery or completion. A callback error is `unknown` because a side effect might already have occurred; the boundary never retries it. SHA-256 detects changes in this proposal's canonical JSON, but does not authenticate the policy, approver, tool implementation, or external result.

An optional host-owned `consumeApproval` callback can atomically claim a grant after the digest matches and policy is rechecked, before the tool callback. It must return exactly `true` for a successful claim. A `false` result blocks with `approval_reused_or_expired`; a claim error blocks with `approval_consume_error`. The claim might already have been spent when its hook throws; reconcile host storage before issuing another grant. The tool callback remains untouched on this blocked path. Policy is checked again after an asynchronous claim. `createLocalOneShotGrants()` illustrates the contract in one Node process with expiry and a synchronous Map deletion. Production use needs a durable atomic store shared across workers, authenticated approval issuance, bounded expiry, audit storage, idempotency, and tool-specific authorization. The opt-in store does not protect unwrapped tools or other processes. This pilot does not replace those controls or the existing ĀML UI governance stack.

`createFileOneShotGrants({ directory })` is the next bounded step: a caller supplies a private **absolute path** to a trusted local filesystem shared by workers on one machine. Issuance writes a short-lived grant record (at most five minutes); a matching claim uses exclusive creation of a marker file. A competing process gets `false` and never reaches the callback. A crash after marker creation leaves the grant spent, even if no tool call occurred. The sample does not clean up issued or claimed records for a long-lived service. Do not put the directory on NFS, a network/synchronized mount, or a path writable by an untrusted user. Node documents that the exclusive flag may not work on network filesystems. The host still needs authenticated approvers, private storage, a trusted clock, lifecycle cleanup, recovery design, idempotency for external effects, and its own permission checks. These are project-authored tests, not independent verification or proof of delivery.

The file-grant store checks the owner, directory type, mode, and symlink state of its root and `issued`/`claimed` children on POSIX before issuance and consumption. Existing paths with any group/other permissions are rejected rather than silently repaired. A failed check throws and the action boundary blocks dispatch through `approval_consume_error`. A consuming worker will not recreate missing child directories. This configuration guard assumes a trusted, stable local path and protects against a mistakenly accessible directory at check time; it cannot defend against a process with the same OS identity changing the path during a filesystem race or an administrator deleting persisted markers. Use a proper store and threat model for production.

### Host-owned dispatch operation ledger (experimental)

`createFileDispatchLedger({ directory })` offers `claim`, `inspect`, and `run` for a **separate host-generated operation ID**. An approval grant answers whether this approval can be claimed once; the operation ID answers whether this particular intended external action has already been attempted. The host must persist the same ID across process restarts or retries, and must generate a new ID only for a genuinely new intent. Do not use the proposal digest alone as the ID: two separately authorized messages can have identical payloads. Never take the ID from model output.

The local directory must be private (owner-only, absolute, trusted local filesystem). `run({ operationId, proposal, executeTool })` freezes the proposal, claims with exclusive creation, and calls `executeTool` only for the winning claim. A duplicate sees `already_returned` or `unknown` without a callback; a changed proposal under the same ID is `mismatch`. The claim is synced before callback. A callback return writes a separate outcome record and yields `returned`; a callback throw yields `unknown`. If a process stops after claiming but before recording its outcome, subsequent attempts remain `unknown`. No success result is stored for replay and no retry occurs. An invalid or incomplete record fails closed. Outcome-write failure after a callback also yields `unknown`.

This utility is not wired to an untrusted agent directly. A host can put the ledger inside its existing `executeTool` callback and treat **anything other than the first `returned` result** as an uncertain boundary—not as permission to invoke the tool again. The receipt's `dispatched` status still means only that a callback returned. If an outside system supports true idempotency keys, use that service's contract too. This file store does not coordinate across machines, network mounts, or tools that bypass the wrapper, and does not implement retention or reconciliation. Permanent claims intentionally prefer missed execution over duplicate execution; investigate uncertain outcomes in the real external system before a human or host authorizes a fresh ID. No human authentication, payment, or delivery is supplied here.

## Why this wedge

Existing agent frameworks provide guardrails, approvals, and traces. Their paths and coverage differ by tool and handoff type. A portable, inspectable action proposal can make the **exact bytes being approved and dispatched** easier to compare across hosts. This is a project-authored interoperability experiment, not a claim of a new industry standard or independent validation. See the [OpenAI Agents SDK tool guardrail documentation](https://openai.github.io/openai-agents-python/guardrails/) and [tool documentation](https://openai.github.io/openai-agents-js/guides/tools/) for examples of current framework controls.
