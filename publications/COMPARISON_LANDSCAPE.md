# Where ĀML Fits

**Status: SHIPPED**

ĀML is easier to understand when compared fairly with adjacent controls.

| Control | Primary question | Typical scope | What ĀML adds |
|---|---|---|---|
| CSP | What code/content sources may load? | Browser resource security | Declared interface meaning and render policy |
| Consent banner | Has a user made a consent choice? | Privacy preference capture | Decision context tied to specific interface output |
| Design system | Is the interface consistent? | UI components and patterns | Declared purpose and inspectable ALLOW/SUPPRESS logic |
| Feature flag | Should this feature be enabled? | Deployment/runtime control | Meaning-level reasoning and receipts |
| Policy engine | Is this action allowed? | General authorization/policy | Human-interface semantics and View Meaning |
| ĀML | Why should this interface element render? | AI/app intent → pixels | Purpose, attention/restoration inputs, decision, receipt |

ĀML is not a replacement for these systems. It is a complementary accountability layer focused on the interface boundary.
