## Follow-up: approval replay and evidence challenge — 2026-11-05

Threat model: an effectful MCP integration supplies a reusable digest approval but omits atomic consumption. With `requires_approval: true`, two calls of the same action both returned `dispatched` in a local pre-fix reproduction. This is a host configuration gap, not a bypass of a correctly configured one-use consumer. The connected SDK pilot now uses a local file grant store and strict gate constructor: in its `approval_replay` case, two attempts produce one child handler audit entry, a first `host_dispatch_returned` receipt, then `approval_reused_or_expired` and zero additional handler calls. Unit test: `test/mcp-call-tool-gate.test.js`. Remaining limits: the approval fixture does not authenticate a person, the direct `/1` boundary permits optional consumption, and local filesystem claims do not solve whole-store rollback or distributed coordination.

An assurance review of the published 13-case challenge found that the runner accepts self-reported callback counts and executed proposals. A lookup adapter can pass by returning public expected outputs without hashing, evaluating policy, or executing. The challenge documentation now limits a runner pass to fixture-output agreement; E4 requires source inspection and independent computation. Runner-owned local effect observation and fresh probes remain open.

A sparse array can also impose work proportional to its declared length inside canonicalization before the 65,536-byte serialized proposal cap is checked. A local probe of one million holes took about 45 ms on the review host before rejection. The guarded-tool and MCP ingress now pass an optional 65,536-element array limit to the canonicalizer, so an array larger than any valid proposal could contain is rejected before allocation or index traversal. Tests use a maximum-length sparse proxy and assert zero index checks and zero callbacks. This is a scoped mitigation; direct use of pinned `dispatchAction`, dense objects, deeply nested inputs, and arbitrary Proxy traps still need proactive resource budgets. No throughput or cross-runtime guarantee follows from the single timing probe.

## Follow-up: mutable target during approval

Threat model: a trusted host's route to an actual service or account changes while an asynchronous approval is pending, and its execution callback consults that mutable route. In a local reproduction against the historical target-bound adapter, the proposal resource was `local:approved`, the approval callback changed the host route to `local:unapproved`, and the callback reported the new destination while the receipt said `dispatched`. This requires a host integration that resolves its target a second time; it is not an untrusted agent modifying the frozen proposal.

The opt-in versioned `dispatchTargetBoundActionV2` checks the resolved target again after one-use claim consumption and before entering the callback, then passes the originally bound target as a separate argument. The regression switches the route during approval: the receipt is `blocked/target_changed`, the claim is spent, and no execution callback runs. A second test constructs the provider request with the pinned target even if mutable host routing changes inside the callback. A missing consumer blocks approval-required v2 calls. Existing `/1` behavior and evidence remain unchanged. These are local host-controlled tests; the adapter cannot force an arbitrary callback to use the pinned argument, prevent a transport/account switch after the check, or prove what a real provider did.

## Follow-up: independently observed local callback channel

A second challenge runner, `scripts/run-action-observed-challenge.mjs`, starts a per-case loopback service and records actual callback requests and proposal JSON. The project reference adapter passed all 13 published and six seeded cases. A static adapter that printed a valid approved plan, receipt, callback count and executed proposal but never invoked the endpoint failed with `observed_callback_count` and `observed_proposal`. Another adapter printed the denied response correctly but contacted the local endpoint anyway; it failed on the same two observed fields. These tests establish that self-reported callback fields alone cannot satisfy the new runner. They do not prove the adapter's internal policy caused the request; the adapter sees the endpoint URL and token and could invoke it directly. The old `/1` challenge remains unchanged for compatibility. The new report is `/2` and is project-authored E2 evidence only.

A mocked MCP account-switch regression held approval for account A, changed the host's live identity to account B, then released approval. The opt-in connection-bound profile bound account A and destination into the proposal resource, spent the grant, and returned `blocked/connection_changed` with zero SDK calls. A stable account A case dispatched once. This depends on a truthful host identity reader tied to the active connection; it is not a connected two-server or real provider test.

## Controlled local provider acknowledgment loss

Three tests invoke a child provider process with exact request bytes, operation ID and digest. In `lost_ack`, the child writes a synced local marker then exits without an acknowledgment; the host records uncertainty, a fresh recovery process reads the marker, and the host records fixture-provider completion without independent confirmation. In `before_write`, no marker exists and the state remains uncertain. In `ack`, the provider returns and the host records completion, again without independent confirmation. The grant cannot be reused and no retry is attempted in any scenario. These are local process and filesystem observations; the host process itself remains alive and the fixture does not model a network partition, power cut, adversarial same-identity file edits, provider idempotency contract or external operation.
